PAI migration — conversations API redesign

Lightspeed Core Stack (LCORE) · OGX removal notes · Sep 2026

This document covers the conversations side of the OGX → pydantic-ai migration: how display history should be stored and exposed once LCORE owns the agent loop, how that differs from pydantic-ai message history used for inference, and the proposed /v3/conversations wire shape (agent runs + ordered items).

1. Decision in one sentence

Ship /v3/conversations as a local display API (items-only agent turns parsed from each pydantic-ai run), while agent context comes from pydantic-ai message-history persistence under the same conversation_id — keep today’s /v1//v2 variants until consumers move.

Preferred baseline:
  • display API ← local DB ← parsed from agent run result
  • agent context ← PAI persistence (same conversation_id)
  • keep /v1 / /v2 as today’s variants
  • ship items-only /v3 (no duplicated messages/tool_*)
  • drop /v1 with OGX · retire /v2 later

2. How to read v1 vs v2 today

/v1/conversations and /v2/conversations are backend variants, not successive API generations:

Surface Store Role
/v1/conversations OGX conversation items (+ app DB metadata) Deprecated; dies with OGX
/v2/conversations LCORE conversation cache Local variant; keep stable as the bridge for current local-DB clients
/v3/conversations (proposed) Unified local display store First true API redesign for agentic history

/v3 is aimed at the industry shift away from plain chat Q/A (user message + assistant reply, tools as side lists) toward an agentic run timeline: ordered items for messages, tool calls/results, retrieval, and outcomes in one sequence.

Avoid: reimplementing /v1 without OGX (blurs the variant story and competes with /v2) · treating /v2 as “the next generation after v1” · shipping duplicate items + messages/tool_* on the wire (OK in SDKs with derived views; wrong for a JSON service API).

3. Hard split: display store vs agent context

LCORE keeps two separate persistence paths that share one id:

  1. Local conversation store + /v3/conversations — used only for displaying history to clients (list / get / update topic / delete). After each agent run, LCORE parses the pydantic-ai run result into a backend-agnostic turn (items[]) and writes it here.
  2. pydantic-ai message-history persistence — used only to feed message history into the next agent run (inference context). It is not what the conversations API returns.

Both use the same conversation_id: the id of the local persistent conversation is the id pydantic-ai uses for its history. They are always logically equivalent records of the same conversation — the same turns and outcomes — but in different formats (display items[] vs PAI message history). The display store is never used to rebuild agent context; PAI history is never used as the conversations API payload.

Key reason for a local conversations API: even where pydantic-ai (or optional packages such as Harness SqliteConversationStore) can list / get / delete threads and persist message history, LCORE still owns a separate display store and /v3/conversations surface. We need a backend-agnostic OpenAPI contract (postgres/sqlite today, not tied to a PAI/Harness store), LCORE-specific fields and items (inline RAG sources, deduped turn citations, topic summary, RBAC, usage, etc.) that are not a 1:1 dump of PAI message parts. PAI persistence remains the source for agent message history; the local API is how clients list, delete, update, and display the same conversation in LCORE’s format.

Concern Store Used for
Display Local SQL (evolved from cache + user_conversation / user_turn) List / get / update topic / delete on conversations API
Agent context pydantic-ai message history keyed by conversation_id Prompting the next run only
Request (conversation_id) → PAI: load message_history[conversation_id] → agent.run → update PAI history → Persist: map run → AgentTurn + items → local display store → Respond: query/stream as today → GET /v3/conversations/{id}: read display store only (never hydrate PAI from it)

Compaction for tokens / context stays in the PAI / context-builder path. The display store may record context_status for UI; those summaries are not re-fed into the agent from SQL.

4. Problems with the shared v1/v2 turn model

Both variants expose the same chat-era shape (ConversationTurn: messages[] + parallel tool_calls[] / tool_results[]). That fits single-shot Q&A; it fights agentic UIs.

Gap Why it hurts
Chat Q/A, not agent run Implicitly one user + one assistant message; no run id / status / usage
Tools beside the timeline Parallel arrays lose multi-round order (text → call → result → text)
Message = role + string No first-class home for retrieval steps, domain errors, optional reasoning
No multimodal inputs Images and other attachments are not first-class on the turn (today they live on the request / transcripts at best); history cannot faithfully show what the user sent beyond plain text
Citations on Message RAG provenance glued to assistant text
Industry direction Ordered heterogeneous sequences (OpenAI output items, Anthropic content blocks, PAI parts) — not sibling tool arrays

5. Proposed /v3 wire shape

5.1 Envelope (mostly unchanged)

GET conversation keeps conversation_id + chat_history (today’s ConversationResponse). v3 also surfaces the conversation-level fields that already exist on list models (ConversationDetails / ConversationData) so clients are not forced to join list + get for metadata: 

{
  "conversation_id": "…",
  "created_at": "2024-01-01T00:00:00Z",
  "last_message_at": "2024-01-01T00:05:00Z",
  "last_message_timestamp": 1704067500.0,
  "message_count": 5,
  "last_used_model": "gpt-4o-mini",
  "last_used_provider": "openai",
  "topic_summary": "…",
  "chat_history": [ /* AgentTurn[] */ ]
}
Field Exists today on Notes
conversation_id GET + list (v1/v2) Unchanged
chat_history GET (ConversationResponse) Same field name; elements become AgentTurn (§5.2)
created_at, last_message_at, message_count, last_used_model, last_used_provider, topic_summary List v1 (ConversationDetails) Include on GET envelope in v3; list can keep the same shape
last_message_timestamp List v2 (ConversationData) Keep for v2-era clients / derived from last_message_at

5.2 AgentTurn (run)

{
  "id": "turn-uuid",
  "status": "completed",
  "agent": null,
  "provider": "openai",
  "model": "gpt-4o-mini",
  "started_at": "2024-01-01T00:01:00Z",
  "completed_at": "2024-01-01T00:01:05Z",
  "context_status": "full",
  "usage": { "input_tokens": 120, "output_tokens": 40 },
  "referenced_documents": [ /* deduped set for the whole run */ ],
  "items": [ /* TurnItem discriminated union — sole body */ ]
}
Field Notes
status completed | interrupted | failed only — no blocked
items Only timeline; do not also ship messages / tool_calls / tool_results
referenced_documents Turn-level deduped set for citation UI (built at persist time)
context_status / usage Same names as QueryResponse / EndEventData
available_quotas Live query/stream only — not on conversation GET
Removed vs v1/v2 turn body: messages, tool_calls, tool_results. That break is why this is /v3, not an additive tweak to /v2.

6. TurnItem discriminated union

Prefer a discriminated union on kind (OpenAPI oneOf) over one merged object with all optional fields. Shared base: id + kind.

kind Attributes Aligns with
user_message content; optional attachments (refs only, no bytes) Request Attachment minus content
assistant_message content Token / turn_complete / QueryResponse.response
tool_call tool_call_id, name, arguments ToolCallSummary (reuse; id → tool_call_id, args → arguments)
tool_result tool_call_id, status, content ToolResultSummary; drop round (order = items[])
sources origin (inline | tool), tool_call_id?, chunks Retrieval step; see §8
error code, message, category?, retryable?, details? Domain outcome only — see §7
reasoning content Optional / forward-compatible; add when product needs it
Extend later (new kinds, not ErrorItem codes): approval / HITL when that feature ships. Do not invent kinds for every failure mode — use namespaced error.code + details.

    "origin": "inline",

    "chunks": [ /* RAGChunk[] for this retrieval */ ]

7. HTTP errors vs ErrorItem

Non-2xx = the API operation failed (nothing useful to put in history, or the request was rejected). ErrorItem inside 2xx = the run was accepted and recorded; the agent outcome failed.

Situation HTTP Persist turn? ErrorItem?
Auth / validation / not found / quota before run 4xx / 429 no no
Dependency down before useful work 5xx / 503 no* no
Model/provider fails mid-run after accept 200 yes (failed) yes
Tool fails but run continues 200 yes no — tool_result.status=error
User interrupt 200 yes (interrupted) optional
Shield refusal 200 yes (completed) no — see §9

*If a placeholder turn was already created, prefer persist + ErrorItem and still return 2xx on the query path.

7.1 ErrorItem shape (extensible)

{
  "id": "…",
  "kind": "error",
  "code": "provider.rate_limit",
  "message": "Upstream model rate limit exceeded",
  "category": "provider",
  "retryable": true,
  "details": { "retry_after_ms": 1200 }
}
Field Role
code Namespaced machine id (domain.reason) — primary extension point
message Safe human text
category Coarse UI bucket: provider | tool | quota | validation | cancelled | internal (expand rarely; no moderation on the public wire)
details Open object for future/code-specific attrs without new top-level fields

Transport errors stay AbstractErrorResponse / SSE ErrorEventData: status_code + response / cause. Map to ErrorItem only when persisting a failed turn: response → message, cause → details.cause — never put status_code on the item.

8. RAG: chunks per item, docs per turn

Data Scope Role
RAGChunk[] Per sources item Evidence for that retrieval step (scores, which search)
ReferencedDocument[] Per turn, deduped set Citation footer for the run

Build the turn-level doc set once at persist time from all sources items (union by document_id / url+title). Do not maintain two independent writers.

8.1 Inline RAG (not a tool)

Inline / pre-query RAG is not a tool call. Represent it as a sources item with origin: "inline" and tool_call_id: null, typically right after user_message:

user_message sources ← origin=inline, chunks for pre-query RAG [tool_call / tool_result …] ← optional real file_search sources? ← origin=tool, tool_call_id set, chunks for that search assistant_message
Avoid: synthesizing a fake file_search tool_call for inline RAG · hanging chunks only on user_message / assistant_message · turn-global chunk lists (loses multi-search attribution).

Prefer one home for chunks: always on sources (inline or origin: "tool" linked by tool_call_id), so storage and OpenAPI stay consistent with tool and non-tool retrieval.

9. Shields / moderation

Preferred: treat shield refusals as a normal completed turn. Stream refusal as tokens; persist as assistant_message; status: "completed"; HTTP 2xx. Keep shield decision / moderation id as internal-only signals (metrics, telemetry, private DB side channel) — not in public conversation JSON.
Do not expose: status: "blocked" · moderation ErrorItem · dedicated SSE blocked event.

10. Streaming payloads — align, don’t fork

Existing StreamEventPayload (discriminator event) is largely sufficient for agentic streaming:

SSE event Persisted as
start Turn correlation (conversation_id / request_id)
token / turn_complete assistant_message
tool_call / tool_result Same-named items (reuse summary models)
end Turn usage / context_status; live citation aggregate OK; persistence uses §8
error / interrupted Transport vs turn status / optional ErrorItem (§7)
compaction Lifecycle only (already on the wire; add to the typed union)

Not missing for v3: reasoning (add later), approval/HITL (add later), mid-stream sources (optional). Streaming stays the only place with token deltas and start/end envelopes; conversation GET never stores those events verbatim.

Cleanup: fold compaction into StreamEventPayload and converge hand-built dicts in streaming_sse.py onto the typed payloads so the union matches what is actually emitted.

Longer term: evolve QueryResponse toward the same AgentTurn / items so sync query, stream reduction, and GET conversation share one schema.

11. Version rollout

  1. Keep /v1 deprecated until OGX removal (do not reimplement without OGX unless a hard external contract requires the path).
  2. Keep /v2 stable for local-DB consumers (additive fixes only).
  3. Implement unified display store + persist path from agent runs.
  4. Ship /v3/conversations with the items-only contract.
  5. Give consumers one adaptation window (v1→v3 or v2→v3).
  6. Remove /v1 with OGX; retire /v2 when traffic is gone.
