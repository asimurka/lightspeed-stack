PAI migration — Conversation compaction

Lightspeed Core Stack (LCORE) · two designs compared · Oct 2026

After OGX removal, long conversations still have to stay inside the model’s context window. This note first states the problem and the stages any compaction pass must run (independent of implementation). It then records how LCORE does that today, describes two PAI-era designs, and chooses one.

  • Design A — rewrite the current additive engine as a pydantic-ai capability.
  • Design B — use harness TieredCompaction (clamp → clear tool results → summarize).

Both designs sit on the same PAI-era split (one conversation_id, two stores). That split is assumed, not compared:

  • Display store — LCORE’s own SQL conversation (turns as items[]). Used only by /v3/conversations so clients can list, get, and show the full thread. After each run LCORE maps the agent result into this format and appends the turn as spoken. Compaction does not rewrite it, so the UI still shows every original user and assistant message.
  • Agent context — pydantic-ai message_history in harness StepPersistence. Used only to prompt the next Agent.run. Continue loads the latest snapshot (continue_run); a branch from an older turn uses fork_run plus new LCORE ids. This list is what compaction shrinks. The next continue already sees the shrunk snapshot — it does not rebuild model context from the display store.

The two records are the same conversation in different formats. Design A vs B is only how the agent list is shrunk. The comparison and the choice are at the end.

1. What compaction is

Each model request carries prior conversation plus the new user input (and tools, instructions, and so on). If that payload exceeds the model’s context window, the provider rejects the call (today: HTTP 413). Compaction shrinks the agent-facing history so the next request still fits, while keeping enough recent context to continue the task.

Compaction is not the UI transcript. Clients still list the full conversation from LCORE’s own store. Only the list handed to the model is rewritten.

1.1 How it is triggered

Before (or as) the model is called, estimate how many tokens the upcoming request will use — prior context and the current input, not prior context alone. Compare that to the model’s context window:

  • Typical rule: compact when estimated tokens ≥ threshold_ratio × context_window and above a token_floor (avoids firing on tiny windows).
  • The window comes from configuration or the model profile. If no window is known, a design may skip the token trigger or use a fallback.
  • How tokens are counted varies (local tokenizer, provider-reported usage plus a guess for new text, or a provider count_tokens API). The trigger idea is the same: used vs window.

1.2 General stages (any implementation)

  1. Load agent history

    Take the message list the next model call would see (previous turns already in agent storage). A new thread has an empty list. A continue loads the latest snapshot. A fork loads history from a chosen earlier point, then starts a new thread id.

  2. Estimate

    Measure that list plus the new user input (and instructions / tools if the estimator includes them). If under the threshold, skip rewrite.

  3. Shrink (only if over threshold)

    Reduce older context. Concrete tactics differ: drop oldest messages, blank old tool results, clamp one huge part, summarize a prefix and keep a recent tail, or a sequence of those. Preserve enough structure that the provider still accepts the list (especially tool-call / tool-return pairing).

  4. Write back, then run

    The rewritten list becomes the run’s live history. The model loop appends this turn. Agent storage snapshots that list. Display storage appends the verbatim turn. The next continue loads the snapshot — already shrunk — and does not rebuild agent context from the UI store.

Load history → estimate (history + this input) → if over threshold: shrink older context → snapshot rewritten history for the agent → append full turn for display Next continue → load latest agent snapshot (already shrunk)

1.3 After OGX: two stores, one id

Same split as in the opening: display store for /v3/conversations, StepPersistence for the model. Compaction mutates only the agent snapshot. Linear continue never concatenates original runs from SQL.

2. Current state (OGX-era LCORE)

Two layers: src/utils/compaction.py (partition, summarize, fold, Red Hat prompts) and src/utils/conversation_compaction.py (request-path integration).

2.1 Policy

  • Additive summaries (spike decision 2): each old chunk is summarized once and kept. Recursive fold only when the summaries themselves approach the limit. PoC: a single rolling summary lost early topics after several cycles.
  • Same model as the user query for the summarize call.
  • Recent verbatim buffer: buffer_turns user/assistant pairs, shrinking until the buffer fits buffer_max_ratio of the window (degrading guard).
  • YAML CompactionConfiguration: enabled (default false), threshold_ratio 0.7, token_floor 4096, buffer_turns 4, buffer_max_ratio 0.3.

2.2 Integration (Option A)

Once any summary exists, LCORE stops passing conversation to OGX inference (OGX would reload the full item list). It builds explicit input: summaries + recent items + this query, sets omit_conversation=True, writes marker messages ([lightspeed:compaction-summary] / [covers:N]), and may persist ConversationSummary rows in the conversation cache (fold needs that cache; A2A is marker-only). After the turn, store_compacted_turn appends the original user input to OGX items for UI.

Trigger estimate includes instructions, summaries, recent items, and params.input (current query). Tokens are tiktoken cl100k_base on type == "message" text only — tool items are skipped. Window from inference.context_windows; missing key → no token trigger. Every compacting request re-fetches OGX items and retokenizes; there is no usage-odometer.

3. Design A — rewrite the current engine as a capability

Keep additive policy, prompts, partition math, and CompactionConfiguration. Move the runtime from OGX request rewriting into a PAI capability that edits message_history already loaded for Agent.run. StepPersistence snapshots the rewritten list; the next continue_run sees compacted history with no extra LCORE summary store.

3.1 Shape

One capability (e.g. AdditiveCompaction) on wrap_run, once per user turn, before handler(). At that point ctx.messages is prior history only — the estimate must also add ctx.prompt / incoming input to match today’s “include this query.” ctx.messages[:] = … writes the shared state.message_history list in place.

Summarize with a bare PAI model call (or a tiny agent without this capability). Represent summaries as ordinary readable messages plus metadata — not provider CompactionPart. Fold by scanning those messages in the list. Compact only on the first step of the run if the hook were before_model_request instead (tool loops). 

@dataclass
class AdditiveCompaction(AbstractCapability):
    enabled: bool = False
    threshold_ratio: float = 0.7
    token_floor: int = 4096
    buffer_turns: int = 4
    buffer_max_ratio: float = 0.3
    context_windows: dict[str, int] = field(default_factory=dict)
    encoding_name: str = "cl100k_base"

    async def wrap_run(self, ctx, *, handler):
        if not self.enabled:
            return await handler()
        history = list(ctx.messages)
        used = estimate_used_tokens(history, ctx.prompt, tokenizer=estimate_tokens)
        window = resolve_window(ctx.model, self.context_windows)
        if window is None or not should_compact(used, window, self):
            return await handler()
        old, recent = partition_model_messages(
            history,
            available_budget_tokens=int(window * self.buffer_max_ratio),
            buffer_turns=self.buffer_turns,
            encoding_name=self.encoding_name,
        )
        if old:
            summary = await summarize_chunk_pai(model=ctx.model, old_messages=old, ...)
            history = inject_summary_messages(summary, recent)
            history = maybe_fold_summaries(history, window, self.threshold_ratio, ctx.model)
            ctx.messages[:] = history
        return await handler()

3.2 What must be adapted

  • Partition: OGX user/assistant pairs → PAI ModelRequest / ModelResponse, preferably grouped by run_id (one agent turn including tools).
  • Transcript / token estimate: walk parts, not type == "message". Optionally replicate a usage anchor (last ModelResponse.usage + tiktoken on the suffix) so later turns do not retokenize the whole list.
  • Replace client.responses.create(..., store=False).
  • Tool pairing and oversized parts are not in the current engine; A does not gain them unless we add them.

3.3 Effort

Medium: capability shell is small; main work is the PAI message adapter, tests, and deleting Option A call sites. Persistence after that is automatic. Config maps 1:1. Product parity with spike decision 2 is the reason to pick A.

4. Design B — harness TieredCompaction

Docs: Harness compaction. Not in LCORE deps today (pydantic-ai==2.27.1). Latest harness implies a PAI version bump.

Do not attach SummarizingCompaction alone. Use TieredCompaction: run cheap edits first, re-measure, stop when under target_fraction / target_tokens. Inner tier max_* is ignored inside the ladder (must still be a valid value). Shrink happens in before_model_request (every model call in the run, including after tools, if still over).

Estimation is built in: last response with usage.input_tokens as an odometer, plus local estimate of newer text (tokenizer= or ~4 chars/token). Pass LCORE estimate_tokens as tokenizer. Explicit context_window for WatsonX / vLLM ids that genai-prices will not know. Chat Completions models are fine; this is not OpenAI Responses server compaction.

4.1 Tiers

Order is intentional — clamp, then clear tools, then summarize — not interchangeable. Harness documents clamp as the first tier of TieredCompaction, before ClearToolResults (docs; rationale in pydantic-ai-harness#286): clamp only rewrites oversized assistant text / tool-call args; tool returns are out of its scope. Clear tools cannot fix a runaway ModelResponse, and summarize would feed that blob into another LLM call and hit the same cap. The ladder stops as soon as history fits the target, so if clear ran first and reclaimed enough, clamp would never run and a huge assistant part could remain. Summarize stays last (only LLM cost).

  1. ClampOversizedMessages — zero LLM. Head/tail truncates one runaway part (assistant text / tool-call args). LCORE has no equivalent.
  2. ClearToolResults — zero LLM. Blanks old tool returns in place; last keep_pairs cycles stay full. Does not delete messages (pairing stays valid).
  3. SummarizingCompaction — LLM only if still over. Verbatim tail is keep_messages (message count, tool-safe), not LCORE turn pairs. Default incremental=True: one living summary, prefix dropped from live history. 
from pydantic_ai import Agent
from pydantic_ai_harness import (
    ClampOversizedMessages,
    ClearToolResults,
    SummarizingCompaction,
    TieredCompaction,
)
from utils.token_estimator import estimate_tokens

CONTEXT_WINDOW = 128_000
THRESHOLD = 0.7
tokenizer = estimate_tokens

compaction = TieredCompaction(
    tiers=[
        ClampOversizedMessages(
            max_part_tokens=50_000,
            keep_head_chars=2_000,
            keep_tail_chars=2_000,
            tokenizer=tokenizer,
        ),
        ClearToolResults(
            max_tokens=1,
            keep_pairs=3,
            min_clear_tokens=500,
            tokenizer=tokenizer,
        ),
        SummarizingCompaction(
            max_messages=1,
            keep_messages=20,
            tokenizer=tokenizer,
            context_window=CONTEXT_WINDOW,
            incremental=True,
            preserve_first_user_message=True,
            keep_user_messages=True,
        ),
    ],
    target_fraction=THRESHOLD,
    context_window=CONTEXT_WINDOW,
    fallback_context_window=CONTEXT_WINDOW,
    tokenizer=tokenizer,
)

agent = Agent(
    chat_model,
    capabilities=[
        compaction,
        # StepPersistence(...), shields
    ],
)

Neither design is a silent swap for today’s product. A keeps additive chunks and buffer-turns policy. B keeps “stay under the window” with a different shrink menu and a different summary shape.

6. Choice — Design B

Choose Design B (harness TieredCompaction with the three tiers in §4) for the PAI / OGX-removal milestone.

The facts that decide it, after the comparison:

  1. Agent persistence is no longer a reason to keep the LCORE engine: both designs snapshot rewritten PAI history. Markers, omit_conversation, and the summary cache go away either way.
  2. The PAI agent loop is tool-heavy. Today’s engine does not count or shrink tool payloads. B’s first two tiers are built for that; A would have to grow them in the same milestone as providers, Responses, and conversations.
  3. Remaining A work is still a medium message/turn adapter. B is wiring plus a version bump, with tiktoken, window, and optional Red Hat prompt still injectable.
  4. Additive chunks are still generally better for fidelity than what SummarizingCompaction does by default — an incremental (rolling) summary: one living document updated in place, earlier topics diluted across cycles (the PoC’s recursive failure mode). That gap is real on paper, but in practice almost empty for LCORE: modern context windows mean a conversation rarely hits the summarize tier at all, and with clamp + ClearToolResults ahead of it the expensive LLM step is rarer still. Reaching several summarize cycles in the same conversation — where the PoC’s topic loss showed up — is an edge case; doing that twice is rarer. Functional debt from shipping B without additive is therefore near zero for the cutover. Keep A as a later CompactionStrategy tier only if quality evidence appears.
B is not “current LCORE compaction in another package.” Do not claim keep_messages equals buffer_turns, or that an incremental summary equals additive chunks. The delivery call is still B; treat additive as optional follow-up, not a silent assumption of B.

7. Delivery checklist (Design B)

  1. Shared agent run, LCORE-owned ids, StepPersistence (continue_run / fork_run).
  2. Add harness (compatible PAI). Wire §4.1 tiers from CompactionConfiguration + context_windows.
  3. tokenizer=estimate_tokens, explicit windows for WatsonX / vLLM, optional LCORE summarization prompt.
  4. Remove Option A from query / streaming / responses / a2a.
  5. Drop summary cache and marker writes; keep display verbatim; optional context_status on display.
  6. Bridge streaming compaction SSE from harness compact events where the LCORE API still exposes it.
  7. Tests: under/over fraction; cheap tiers skip summarize; clamp oversized part; continue sees rewritten history; fork from pre-compaction run_id; missing usage; custom provider window.
  8. Follow-up only if quality requires additive chunks: Design A as last tier or as replacement of SummarizingCompaction.
