PAI migration — tools, MCP, file_search

Lightspeed Core Stack (LCORE) · focused notes for OGX removal · Sep 2026

This document covers only the tools side of the OGX → pydantic-ai migration: how MCP, file_search / RAG, and skills should run once LCORE owns the agent loop. It does not cover inference provider adapters, conversation CRUD, or the Responses HTTP adapter — those are separate workstreams.

Scope is LCORE’s officially supported inference providers (providers.md): OpenAI, Azure, VertexAI, WatsonX, AWS Bedrock, RHOAI (vLLM), and RHEL AI (RHAIIS/vLLM). After OGX removal, tools must behave the same on that whole set. MCP is local only (agent-process MCP client) — provider-hosted MCP is out of scope. Wiring: MCP capability with a configured MCPToolset as local= (see §4.1).

1. Decision in one sentence

Post-OGX, LCORE should treat MCP, file_search, and skills as agent-executed function tools — from the model’s point of view these are ordinary tool calls that the agent process runs and returns. That path is the same for every supported inference provider.

Preferred baseline: one LCORE-owned file_search / RAG tool + local MCP via MCP(native=False, local=MCPToolset(...)) + existing skills as function tools. In message history that shows up as ToolCallPart → LCORE/agent executes → ToolReturnPart.

2. Function tools (LCORE path)

Pydantic-ai can also wire some features as provider-native tools, but LCORE’s baseline is the function-tool path: the model emits a tool call, pydantic-ai pauses the loop, LCORE (or an in-process MCP client) runs the tool, and a tool return is fed into the next model request.

Docs: Function tools, Message parts.

Kind History parts Who executes When to use in LCORE
Function tools ToolCallPart → agent → ToolReturnPart LCORE / pydantic-ai agent process Only path for MCP, file_search, skills

That loop is provider-agnostic across OpenAI, Azure, VertexAI, WatsonX, Bedrock, and vLLM. One LCORE-owned path keeps behavior, auth, corpora, timeouts, and telemetry identical for the whole supported set.

3. file_search / RAG

“file_search” means: the model may call a retrieval tool during generation. LCORE already has retrieval (BYOK, OKP, vector search utilities). The migration question is whether that retrieval stays our tool over LCORE corpora, or we use a provider’s hosted file-search / vector-store API where one exists.

3.1 Native file_search on LCORE-supported providers

Mapped from pydantic-ai’s FileSearchTool table (docs) onto LCORE’s supported set only:

LCORE-supported provider Native FileSearchTool? Notes
OpenAI (Responses API) ✅ OpenAI vector stores (Files API). Not Chat Completions.
Azure OpenAI ⚠️ / limited Only if the deployment exposes the same Responses + vector-store surface as OpenAI; not assumed for every Azure setup.
Google VertexAI ❌ PAI marks Vertex-style as unsupported for FileSearchTool (distinct from Gemini API file search, which LCORE does not support as a provider).
IBM WatsonX ❌ Not supported.
AWS Bedrock ❌ Not supported.
RHOAI / RHEL AI (vLLM) ❌ OpenAI-compat Chat Completions; no native file_search.

Even on OpenAI Responses, the corpus lives in the provider’s vector store, not in LCORE BYOK/OKP. Most of the supported set has no native file_search at all.

3.2 Options

Option What it is Pros Cons
A. LCORE custom tool (preferred) Register an @agent.tool (or capability) that calls LCORE vector search / BYOK / OKP Same on all supported providers; reuses existing retrieval; filters, max_chunks, auth stay in LCORE We own latency, failures, and result formatting
B. PAI FileSearchTool (native) NativeTool(FileSearchTool(file_store_ids=[…])) where the provider hosts it Less retrieval code on OpenAI Responses (and some Azure) Missing on VertexAI / WatsonX / Bedrock / vLLM; corpus is not LCORE BYOK; conflicts with dropping OGX vector-store proxy
C. Mix A + B Dual implementation Possible latency win on OpenAI Two RAG contracts; harder parity tests — not preferred
Prefer A. Native file_search exists on OpenAI Responses (and possibly some Azure), but LCORE must also serve VertexAI, WatsonX, Bedrock, and vLLM with the same BYOK/OKP corpora. One LCORE retriever (tool + optional inline adapter) is the consistent design.

Inline RAG (inject context before the model call) remains a related but separate feature. The important migration point is that the tool form of retrieval replaces what OGX used to execute as native file_search on supporting stacks. Sharing one core retrieve function between inline and tool adapters is fine; both still stay LCORE-owned. 

from pydantic_ai import Agent, RunContext
from pydantic_ai.tools import Tool

from configuration import configuration

async def file_search(ctx: RunContext[None], query: str) -> dict:
    sources = list(configuration.rag.retrieval.tool.sources or [])
    max_chunks = configuration.rag.retrieval.tool.max_chunks
    return {"chunks": [], "documents": []}

agent = Agent(
    model,
    tools=[Tool(file_search, name="file_search")],
    capabilities=[*existing_capabilities],
)
result = await agent.run(prompt)

Attach only when tool RAG is enabled. Keep per-request with the agent (same lifecycle as MCP). Inline RAG can share the same retrieve helper.

4. MCP (local only)

MCP servers expose tools over the Model Context Protocol. After OGX removal, LCORE (via pydantic-ai) must connect to those servers from the agent process, advertise their tools to the model, and execute calls when the model requests them — with the same per-request credentials LCORE already supports.

LCORE does not use provider-hosted MCP. Baseline is a local MCP client only, wired as an MCP capability that wraps a configured MCPToolset (see §4.1).

Docs: MCP overview, MCP client / MCPToolset, Per-user authentication.

4.1 MCP capability + MCPToolset

Two local entry points; both run tools in the agent process as function tools. The capability’s local path can build an MCPToolset itself, or accept a fully configured one via local=.

MCP capability alone MCPToolset via toolsets=
Pros Primary PAI entry point; attaches via capabilities= with shields/skills; room for a later native=True without changing the config schema Full client knobs (timeouts, headers, http_client, process_tool_call); local-only by construction
Cons Thin client API if used without local=; must keep native=False on LCORE’s supported providers today Parallel attachment path if used bare; no capability-level native upgrade path
Decision: use both — one MCP capability per configured server with native=False and a fully configured MCPToolset as local=. Attach via capabilities= (the capability’s toolset still flows into Agent.toolsets).

That keeps the capability as the agent-facing unit (discovery, future native upgrade) while putting timeouts, headers, and other client options on the toolset LCORE already needs for today’s registry. 

from pydantic_ai import Agent
from pydantic_ai.capabilities import MCP
from pydantic_ai.mcp import MCPToolset

from utils.mcp.mcp_headers import build_mcp_headers

# Per HTTP request — same merge as today’s get_mcp_tools / InputToolMCP
merged = build_mcp_headers(config, mcp_headers, request.headers, token)

mcp_capabilities = []
for server in configuration.mcp_servers:
    # skip servers whose configured auth did not resolve for this user
    toolset_id = f"mcp:{server.name}"
    toolset = MCPToolset(
        server.url,
        id=toolset_id,
        headers=merged.get(server.name, {}) or None,
        include_instructions=True,
        read_timeout=float(server.timeout) if server.timeout else None,
    )
    mcp_capabilities.append(
        MCP(server.url, native=False, local=toolset, id=toolset_id)
    )

agent = Agent(model, capabilities=[*existing_capabilities, *mcp_capabilities])
result = await agent.run(prompt)

Use headers= on the toolset for the full LCORE merge. A lone bearer drops custom and propagated headers (e.g. x-rh-identity).

4.2 Multi-user authentication

LCORE merges per-request credentials in build_mcp_headers (config secrets, MCP-HEADERS, K8s / client / oauth tokens, allowlisted propagated headers such as x-rh-identity) and already builds a new agent per request. Keep doing the same for MCP: construct fresh MCP + MCPToolset pairs with that request’s merged headers= — identical to today’s new InputToolMCP objects in get_mcp_tools. No shared/cached client across users; no new auth architecture. (PAI per-user auth)

5. Skills and other function tools

Agent skills and other custom functions are already modeled as tools that LCORE / the agent executes. Removing OGX does not change that contract: they remain pydantic-ai function tools or capabilities attached to the agent, on the same client-side path as MCP and file_search.

Lifecycle matches MCP: skills are wired when build_agent runs for that request (via _agent_capabilities), not as a long-lived shared toolset across concurrent users. Keep that per-request attachment after OGX removal.

6. Parsing agent responses (tool_processor)

Today, streaming and non-streaming agent helpers (utils/agents/streaming.py, utils/agents/query.py) reduce pydantic-ai message parts into LCORE turn summaries via utils/agents/tool_processor.py. That module has two pipelines:

Part types Processor What LCORE emits today
ToolCallPart / ToolReturnPart process_function_tool_* Generic function_call / function_call_output (string content)
NativeToolCallPart / NativeToolReturnPart process_native_tool_* Typed summaries: file_search_call, mcp_call, mcp_list_tools, web_search_call; plus rag_chunks / referenced_documents for file_search

Under OGX / provider-native tools, file_search and MCP arrive on the native path. summarize_native_tool_call / process_native_tool_result match on FileSearchTool.kind and names prefixed with MCPServerTool.kind:, then run specialized helpers (summarize_file_search_result, summarize_mcp_tool_result, …) that know the provider’s return shape (OpenAI file-search result rows, MCP list vs call payloads).

With the preferred baseline — LCORE file_search as an @agent.tool and a local MCP client (MCP + MCPToolset) — file_search and MCP are no longer native. They show up as ordinary function-tool parts: ToolCallPart → LCORE/MCP client executes → ToolReturnPart. The native match arms for FileSearchTool / MCPServerTool simply never fire for those product features.

If we only flip registration and leave tool_processor unchanged: MCP and file_search collapse into generic function_call / function_call_output. SSE and conversation turn summaries lose typed mcp_* / file_search_call events, and rag_chunks / referenced_documents stop being filled from the native file-search parser.

6.1 What must move to the function-tool path

Feature Today (native) After switch (function tools)
file_search NativeTool* + FileSearchTool.kind → type="file_search_call", parse OpenAI-shaped results into RAGChunk / ReferencedDocument ToolCallPart / ToolReturnPart for the LCORE tool name. Return payload must be a known shape (or the tool must return structured data) so a new function-tool summarizer can rebuild the same RAG fields — not part.model_response_str() alone.
MCP Native name mcp:… + action / tool_args → mcp_list_tools or mcp_call Local MCP client exposes each remote tool as a normal function tool (tool name = MCP tool name, not MCPServerTool.kind:label). Need naming / metadata conventions (e.g. server label, list vs call) if API clients still expect type="mcp_call" / mcp_list_tools.

6.2 Practical migration notes for tool_processor

  • Extend summarize_function_tool_call / summarize_function_tool_result (or add LCORE-specific helpers) to recognize the file_search tool and MCP tools by name / return schema, and emit the same ToolCallSummary / ToolResultSummary types the UI and /v2/conversations already consume.
  • Move RAG document/chunk extraction off OpenAIFileSearchResult / native content dicts onto whatever the LCORE retriever returns from the function tool (reuse build_referenced_document / rag_chunks_from_* ideas with LCORE’s own hit shape).
  • Native handlers for FileSearchTool / MCPServerTool become unused for the product path (safe to keep briefly for leftover history, or delete once nothing emits those parts). WebSearchTool is unrelated unless we also move it client-side.
  • Message history for the next turn will store ToolCallPart / ToolReturnPart for these features, not NativeTool* — that is correct for continuation; the API projection layer is what must be taught the new shapes.
