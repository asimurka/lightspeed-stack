PAI migration — Responses API (LCORE rewrite)

Lightspeed Core Stack (LCORE) · OGX removal notes · Oct 2026

How /v1/responses should run after OGX removal: keep the public OpenAI-compatible Responses HTTP contract, replace AsyncOgxClientHolder.get_client().responses.create with a per-request pydantic-ai Agent, and wrap that agent with a Responses input/output adapter.

This document covers the Responses HTTP adapter only — especially preserving today’s client function vs MCP execution split, and projecting PAI results into the Responses envelope. Topics owned by other migration notes are linked, not restated.

1. Decision (one sentence)

Recommended: one pydantic-ai agent loop per request, two HTTP projectors (OpenAI Responses envelope vs LCORE query SSE). Preserve today’s OpenResponses tool semantics: request function tools break the loop for the external agent; request and config mcp / file_search / skills execute in-process. Do not keep an OGX Responses pass-through.
Avoid: calling OGX responses.create · treating all request.tools as deferred · a homemade conversation copy for previous_response_id · pre-run OGX shield HTTP plus shield_violation_generator · compaction via omit_conversation · adopting PAI Agent.to_responses() as the LCORE endpoint (text-only; hides server tool calls) · per-provider settings translators for common knobs (§8).

2. Assumptions (covered elsewhere)

By cutover these land in their own docs; Responses is a consumer:

  • Providers registry — get_model, profiles, ModelSettings resolver.
  • Prompts — resolve request.prompt → instructions, strip id, echo.
  • Tools / MCP / file_search / skills — local MCP(native=False, local=MCPToolset), LCORE file_search function tool, skills as capabilities.
  • Conversations redesign — display store + persist mapper (PAI run → turn items).
  • Compaction — harness TieredCompaction (Design B), not omit_conversation.
  • Stream interrupt — cancel token / interrupted SSE (query path; Responses may share later).

Query / streaming query share the same agent loop after cutover; only the projector differs (utils/agents/query.py, utils/agents/streaming.py).

3. Target architecture

Request path (non-stream and stream share the middle):

Always project PAI events into the LCORE Responses envelope for /v1/responses. Do not return raw PAI / OpenAI SDK objects as the public body.

5. Shields as wrap_run capabilities

Input and output moderation run inside the agent, not as a second HTTP round-trip to OGX. Existing LCORE capabilities (QuestionValidity, Granite Guardian, PiiRedaction) wrap Agent.run / stream. Order: shields outermost so a refusal never starts (or continues) the model loop.

Recommended: capability refuses → projector still returns a completed Responses object (or stream that ends in response.completed) with a refusal payload. Persist that as a normal turn.
Avoid: keeping run_shield_moderation_v2 plus the agent · a dedicated shield_violation_generator · failing the HTTP request with 4xx for a content-policy refusal.

6. Tools — preserve today’s OGX Responses semantics

How to register and discover MCP, file_search, and skills is in pai-tools-mcp-filesearch-summary.html. This section is only what /v1/responses must preserve from today’s OGX pass-through: who executes which OpenResponses tool type, and how the external agent resumes.

6.1 What OGX does today (baseline to keep)

LCORE resolves / merges tools, then forwards the OpenResponses tool list to client.responses.create. OGX owns the loop:

OpenResponses tools[] entry Who executes Public result
type: "function" (from request) External agent — loop breaks function_call; next request brings function_call_output
type: "mcp" (request or config) Backend connects to server_url and runs mcp_call / mcp_list_tools (with output)
type: "file_search" (config / request) Backend file_search_call

LCORE’s “client vs server” split today is post-hoc filtering for storage / metrics / stream (is_server_deployed_output), not a different execution path for MCP:

  • function_call → always client (pass through; skip turn summary).
  • mcp_* with server_label in LCORE config → server.
  • mcp_* with any other label → client for filter only (still executed by the backend if reachable).

X-LCS-Merge-Server-Tools: true only changes which tools are sent into the loop (client list ∪ config list + 409 on conflicts). See responses.md § Server-Tool Merging.

6.3 Resume (external agent, function tools only)

Unchanged wire contract. After a response that includes function_call, the external agent runs the tool and POSTs again: 

{
  "previous_response_id": "<prior run_id>",
  "input": [
    { "type": "function_call_output", "call_id": "fc_1", "output": "…" }
  ],
  "tools": [ /* same function (+ optional mcp) declarations as needed */ ]
}

Adapter: tip → continue_run + new run_id; map function_call_output items → DeferredToolResults(calls={call_id: output}). Client MCP does not use this path when it was executed in-loop.

6.4 tool_choice and filters

Keep today’s LCORE resolution (resolve_tool_choice / resolve_client_tool_choice, allowed-tools filter, tool_choice=none → no tools). After assembly, map onto PAI PrepareTools / first-step tool_choice callable using profile flags from the providers registry — do not special-case backends here.

6.5 Output filter (unchanged product rule)

Keep is_server_deployed_output behavior when merge streaming is on: hide server MCP noise from the client stream; pass through function_call and non-config MCP labels; exclude client items from turn summary / metrics / storage.

7. previous_response_id — continue vs fork

Display CRUD and the turn model live in conversations redesign. Agent history snapshots and compaction interaction are in compaction. Responses owns the tip-vs-fork policy for previous_response_id (same rule as today’s resolve_response_context).

LCORE always mints conversation_id and run_id into Agent.run. Public response.id is that run_id. continue_run / fork_run only load messages; they do not assign ids.

Request History conversation_id run_id
No conversation / previous response None mint mint → response.id
Continue: request conversation, or previous_response_id == last_response_id continue_run(store, run_id=prior_run_id) keep mint (must not already appear in history)
Fork: previous_response_id != last_response_id fork_run(store, run_id=previous_response_id) mint new (explicit string, not 'new', not omitted) mint 
# tip: linear continue
history = await continue_run(store, run_id=previous_response_id)
result = await agent.run(
    prompt, message_history=history,
    conversation_id=existing_conv_id, run_id=str(uuid4()),
)

# not tip: fork off that snapshot
history = await fork_run(store, run_id=previous_response_id)
result = await agent.run(
    prompt, message_history=history,
    conversation_id=str(uuid4()), run_id=str(uuid4()),
)
Avoid: conversation_id='new' · omitting conversation_id after fork_run (inherits parent thread) · fork_run on every previous_response_id · reusing previous_response_id as run_id · conversation-head overwrite only (mid-chain fork cannot load).

8. OpenResponses settings → provider ModelSettings

How advanced OpenResponses request fields become per-backend knobs. Profile tables and resolve_model_settings live in pai-providers-registry.html §7; this section is the Responses-side mapping policy.

Decision: one OpenResponses → PAI ModelSettings translator, then profile resolve. Do not write a separate settings translator per inference provider for common knobs (temperature, max_tokens, …). PAI’s model class already puts supported ModelSettings keys on that provider’s wire; the profile says what the model id can honor.

8.1 Layers

OpenResponses request fields │ ▼ LCORE: one translator (§8.2–§8.4) → shared ModelSettings (+ rare openai_* / thinking) → agent output_type from text.format (§8.4) → agent args for tools / input / conversation │ ▼ resolve_model_settings(profile, requested) (providers doc) drop unsupported + warnings; 400 only cannot-start / output-contract (incl. text.format the profile cannot honor) │ ▼ Agent(..., output_type=…) Agent.run(..., model_settings=applied) │ ▼ PAI Model class → provider wire (automatic per model type)

8.3 Responses as client of the resolver

  1. Accept any settings that pass the public Pydantic request schema (do not 400 only because a backend “usually ignores” a field).
  2. Map once (§8.2) → call get_model_profile + resolve_model_settings → ModelSettings for Agent.run.
  3. Echo the applied (resolved) values on the Responses object, not the raw request blob.
  4. Surface coercions / drops as warnings (response warning / log), not silent omission.
  5. HTTP 400 only for cannot-start or output-contract. Shield refusals stay completed (§5).
Avoid: a Bedrock / WatsonX / vLLM / Vertex settings translator each · stuffing the whole Responses body into extra_body on every backend · catching PAI UserError to probe capability · forwarding openai_previous_response_id / openai_native_tools as the post-OGX continuation or tools path (LCORE owns those via §6–§7).

Seed code today: src/pydantic_ai_lightspeed/ogx/_model.py (_model_settings_from_responses_params) — retarget from OGX-oriented OpenAIResponsesModelSettings + extra_body toward unified ModelSettings plus the narrow openai_* set above. Today text is stuffed into extra_body for OGX; after cutover it becomes output_type (§8.4), not extra_body.

8.4 text attribute in practice

OpenResponses shape (from responses.md / OpenAIResponseText): 

{
  "text": {
    "format": {
      "type": "text" | "json_object" | "json_schema",
      "name": "…",           // json_schema
      "description": "…",    // json_schema
      "schema": { … },       // json_schema (JSON Schema object)
      "strict": true         // json_schema
    },
    "verbosity": "low" | "medium" | "high"   // optional; default medium
  }
}

Important: format selects the agent’s output_type. Only verbosity is a model setting (openai_text_verbosity). Do not forward text via extra_body after OGX removal.

def output_type_from_text(text, *, need_deferred: bool):
    """Map OpenResponses text → Agent output_type."""
    fmt = None if text is None else text.format
    kind = None if fmt is None else fmt.type

    if kind is None or kind == "text":
        base: object = str
    elif kind == "json_object":
        base = NativeOutput(  # or PromptedOutput if profile requires
            StructuredDict(
                {"type": "object", "additionalProperties": True},
                name="json_object",
            )
        )
    elif kind == "json_schema":
        if not fmt.schema:
            raise cannot_start("text.format.schema required")
        schema_type = StructuredDict(
            fmt.schema, name=fmt.name, description=fmt.description
        )
        base = NativeOutput(
            schema_type,
            name=fmt.name,
            description=fmt.description,
            strict=fmt.strict,
        )  # swap for ToolOutput / PromptedOutput per profile
    else:
        raise cannot_start(f"unsupported text.format.type: {kind}")

    if need_deferred:
        return [base, DeferredToolRequests]
    return base

# settings side (only verbosity):
if text and text.verbosity is not None:
    model_settings["openai_text_verbosity"] = text.verbosity

8.4.2 Projector / public envelope

OpenResponses still returns a normal message / output_text item. For json_object / json_schema, put the serialized JSON (from result.output) in output_text.text — same shape clients see today through OGX. Do not invent a separate structured-output item type on the wire.

  • Plain text → str(result.output) in output_text.
  • Structured → json.dumps(result.output) (dict from StructuredDict / model dump) in output_text.
  • Deferred function calls still take precedence as function_call items when result.output is DeferredToolRequests (§6 / §10).
Avoid: mapping text into ModelSettings.extra_body · requiring a Pydantic model class per client schema (use StructuredDict) · 400 on every backend that lacks native JSON schema when prompted/tool mode would work · treating verbosity as cross-provider (it is openai_* only).

10. Output adapter (agent → Responses)

Goal: consume PAI run streaming events and produce an async iterator of OpenResponses-compatible events on the fly (then optionally SSE-encode them). Do not mount PAI Agent.to_responses() (not shipped for our pin; text-only; hides in-loop tools). Do not put the projector on the agent — Agent has no projector slot.

Recommended: subclass PAI UIEventStream (from pydantic_ai.ui import UIEventStream, impl in pydantic_ai.ui._event_stream) as OpenResponsesEventStream. LCORE keeps building the agent and run kwargs (§6–§9); the stream class only transforms. A full UIAdapter is optional — useful later if we want dispatch_request, but not required for the projector.

10.1 How UIEventStream works

Template-method dispatcher. You override fine-grained handle_* hooks (and abstract encode_event). You call only transform_stream (and optionally encode_stream). The base class invokes your overrides.

agent.run_stream_events(...) → AsyncIterator[NativeEvent] │ ▼ OpenResponsesEventStream.transform_stream(native) │ ├─ before_stream() → e.g. response.created ├─ for each NativeEvent: │ handle_event(event) # base match/dispatch │ → handle_part_start/delta/end │ → handle_text_* / handle_tool_call_* / … │ → handle_function_tool_* / handle_run_result / … ├─ on_error / on_cancelled └─ after_stream() │ ▼ AsyncIterator[OpenResponses event objects] │ optional encode_stream / encode_event ▼ SSE strings (text/event-stream)

Important hooks for Responses: before_stream, handle_text_start/delta/end, handle_tool_call_* / handle_function_tool_* (server-executed tools vs deferred client functions), handle_run_result (completed / DeferredToolRequests), on_error, encode_event. Docs: UIEventStream API.

10.2 Unify stream and non-stream

PAI has no “AgentRunResult → one Responses JSON” helper. Do not keep a second mapper for stream=false. Both HTTP modes use the same agent API and the same OpenResponsesEventStream. The request flag only chooses packaging.

stream=true stream=false
Agent run_stream_events (always)
Transform transform_stream → OpenResponses events
HTTP encode_stream → SSE buffer events; return the completed Responses object as JSON (encode_event unused)

Non-stream is a buffered stream: handlers still emit response.created, deltas, tool items; LCORE does not flush them. The JSON body is the snapshot at response.completed / response.failed (same output[] the SSE client would have accumulated). Keep that snapshot on the projector (mutate a running Responses object in the handlers, or fold the event list at the end).

Avoid: agent.run plus a parallel result→JSON mapper · encoding SSE and then parsing it back into JSON for non-stream.

10.3 How LCORE will use it

  1. Build agent + run args as today in this doc (tools, settings, output_type, history, minted run_id).
  2. Construct OpenResponsesEventStream(response_id=run_id, …) with run_input=None (standalone encoder mode — no UIAdapter).
  3. Always open agent.run_stream_events(…) and transform_stream.
  4. If stream: encode_stream → FastAPI StreamingResponse. Else: drain the event iterator and return the projector’s final Responses object as JSON.
  5. Inside handlers: apply §6.5 client/server filter (hide server MCP noise when merge streaming; pass through client function_call).
projector = OpenResponsesEventStream(response_id=run_id, model=…)

async with agent.run_stream_events(prompt, run_id=run_id, …) as native:
    events = projector.transform_stream(native)
    if stream:
        async for chunk in projector.encode_stream(events):
            yield chunk  # OpenResponses SSE
    else:
        async for _ in events:
            pass
        return projector.final_response  # one JSON body
Avoid: a free-standing for ev in events giant switch when UIEventStream already provides the dispatch · overriding handle_event without calling super() · using stock AG-UI / Vercel adapters as the public Responses wire · treating custom toolsets as the event projector (toolsets execute; this class formats).

10.5 Failures (HTTP vs stream)

  • Validation / cannot-start / output-contract → HTTP 400 (before the agent runs).
  • Auth / quota → 401 / 403 / 429.
  • Provider outage → 502/503 as today.
  • Shield refusal → completed Responses (or stream completed) with refusal content.
  • Mid-run tool or model error → on_error → response.failed; persist ErrorItem.
