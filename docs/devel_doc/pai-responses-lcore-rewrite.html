PAI migration — Responses API (LCORE rewrite)

Lightspeed Core Stack (LCORE) · OGX removal notes · Sep 2026

How /v1/responses (and the shared query / streaming-query agent path) should run after OGX removal: keep the public OpenAI-compatible Responses HTTP contract, replace AsyncOgxClientHolder.get_client().responses.create with a per-request pydantic-ai Agent, and wrap that agent with a Responses input/output adapter.

This document covers the Responses HTTP adapter only. It assumes a providers registry (get_model, profiles, settings resolution), a local prompt store, local MCP plus an LCORE file_search function tool, and a conversation persist mapper are already in place.

1. Decision (one sentence)

Recommended: one pydantic-ai agent loop per request, two HTTP projectors (OpenAI Responses envelope vs LCORE query SSE). LCORE owns assembly, filtration, wraps, and echo; PAI owns the model call, tool execution, and persistence of the run. Do not keep an OGX Responses pass-through.
Avoid: calling OGX responses.create · a homemade conversation copy for previous_response_id · pre-run OGX shield HTTP plus a parallel shield_violation_generator · compaction via omit_conversation · treating PAI UserError as the primary validation path for model options.

2. Assumptions

Concretely, by the time this endpoint is cut over:

  • ProviderRegistry.get_model(provider_id, model_name) returns a PAI Model for the six backends in providers.md.
  • request.prompt is resolved to runtime instructions and stripped from outbound model params.
  • MCP is local (MCP(native=False, local=MCPToolset)); file_search is an LCORE function tool, not provider-hosted FileSearchTool.
  • Conversation load/store uses the redesigned turn model; the persist mapper writes PAI run / TurnSummary → AgentTurn.items.

Query (/v1/query) and streaming query already share helpers with Responses (utils/agents/query.py, utils/agents/streaming.py, build_agent). After cutover they share the same agent loop; only the projector differs.

3. Target architecture

Request path (non-stream and stream share steps 1–7):

auth / quota / conversation load │ ▼ prompt resolve → runtime instructions │ ▼ registry.get_model(provider_id, model_name) │ ▼ assemble tools + filter + tool_choice (§7) │ ▼ resolve ModelSettings against model.profile │ ▼ Agent + wrap_run capabilities (shields + compaction, §5–6) │ ▼ Agent.run / run_stream_events │ ├── projector: OpenAI Responses JSON / SSE (/v1/responses) └── projector: LCORE query SSE (streaming query) │ ▼ persist via conversations mapper

Always project PAI events into the LCORE Responses envelope for /v1/responses. Do not return raw PAI / OpenAI SDK objects as the public body. Streaming query keeps its existing LCORE SSE event names.

5. Shields as wrap_run capabilities

Input and output moderation run inside the agent, not as a second HTTP round-trip to OGX. Existing LCORE capabilities (QuestionValidity, Granite Guardian, PiiRedaction) wrap Agent.run / stream. Order: shields outermost so a refusal never starts (or continues) the model loop.

Recommended: capability refuses → projector still returns a completed Responses object (or stream that ends in response.completed) with a refusal payload. Persist that as a normal turn (shield refusals are completed turns, internal signals only).
Avoid: keeping run_shield_moderation_v2 plus the agent · a dedicated shield_violation_generator that bypasses the projector · failing the HTTP request with 4xx for a content-policy refusal (that is a completed model outcome, not a bad request).

Query vs Responses: same wrap_run stack. Only the projector (OpenAI envelope vs LCORE SSE) changes how the refusal is serialized.

6. Compaction as a ProcessHistory capability

Conversation compaction is an agent capability that rewrites history before the next model call (PAI ProcessHistory / CompactionPart), not an OGX flag that omits the conversation from the request.

  • Trigger and fold-up policy stay LCORE (utils/compaction.py / conversation_compaction.py).
  • The capability emits compaction parts so the persist mapper can record them (the conversation SSE union already includes compaction).
  • Do not pass omit_conversation (or equivalent) to the model transport.

7. Tools and tool_choice

This section is only how Responses selects and constrains the assembled tool set per request — including every filtration option the endpoint has today. MCP registration, lifecycle, and the file_search function tool are assumed already wired on the agent.

7.1 Assembly (LCORE)

  1. Merge config MCP + request MCP + header MCP (existing utils/mcp_headers.py / prepare_tools).
  2. Attach local MCPToolset via MCP(native=False, local=…).
  3. Attach the LCORE file_search function tool when RAG is enabled.
  4. Apply all current filters before the agent starts: allowed_tools / allowed entries, per-server tool allow-lists, disabled servers, and the post-run MCP output filter (that last one stays LCORE; PAI does not know LCORE’s public MCP shape).

7.2 tool_choice (PAI, after LCORE assembly)

PAI PrepareTools plus a first-step tool_choice callable (OpenAI-style auto / none / required / named tool). Map native vs function-tool choice using the model profile flags from get_model_profile — do not special-case backends in the Responses adapter.

Avoid: forwarding OpenAI hosted tool types (file_search, web_search, provider MCP) into PAI native tools on Vertex / Bedrock / vLLM / WatsonX. Those backends do not implement them; LCORE already replaced file_search with a function tool.

7.3 Output projection

Tool calls and results in the Responses object must keep today’s public shapes (MCP call id, file_search citations). Map PAI ToolCallPart / function-tool results onto those shapes in the projector; do not invent a second mapping.

8. previous_response_id and PAI persistence

LCORE always mints conversation_id and run_id and passes both into Agent.run. Public response.id is the run_id we generated for that call. Same tip-vs-fork rule as resolve_response_context today.

continue_run / fork_run only load a snapshot’s messages. They do not assign ids. Fork vs continue is what you pass to Agent.run.

Request History conversation_id run_id
No conversation / previous response None mint mint → response.id
Continue: request conversation, or previous_response_id == last_response_id continue_run(store, run_id=prior_run_id) keep mint (must not already appear in history)
Fork: previous_response_id != last_response_id fork_run(store, run_id=previous_response_id) mint new (explicit string, not 'new', not omitted) mint 
# tip: linear continue
history = await continue_run(store, run_id=previous_response_id)
run_id = str(uuid4())
result = await agent.run(
    prompt,
    message_history=history,
    conversation_id=existing_conv_id,
    run_id=run_id,
)

# not tip: fork off that snapshot
history = await fork_run(store, run_id=previous_response_id)
conv_id = str(uuid4())
run_id = str(uuid4())
result = await agent.run(
    prompt,
    message_history=history,
    conversation_id=conv_id,
    run_id=run_id,
)
Recommended: keep per-run_id snapshots so fork_run(run_id=previous_response_id) can load a mid-chain turn. Display CRUD stays on the LCORE conversation store; the projector echoes our run_id as response.id.
Avoid: conversation_id='new' (PAI mints the thread id) · omitting conversation_id after fork_run (PAI inherits the parent id from message_history — that is still the old thread) · fork_run on every previous_response_id (the tip is a continue) · reusing previous_response_id as run_id (raises UserError) · conversation-head overwrite only (the source run’s snapshot is gone, so a mid-chain fork cannot load).

9. Model settings: what Responses does

Profiles come from factory.get_model_profile; the registry resolver turns that plus request settings into applied ModelSettings. This endpoint does not reimplement that table.

Responses is a client of that resolver:

  1. Accept any settings that pass the public Pydantic request schema (do not 400 only because a backend “usually ignores” a field).
  2. Call factory.get_model_profile then the settings resolver → ModelSettings passed to Agent.run.
  3. Echo the applied (resolved) values on the Responses object, not the raw request blob.
  4. Surface coercions as warnings (response warning / log), not as silent drops.
  5. HTTP 400 only when the resolver classifies the request as cannot start or as an output-contract failure (JSON schema / structured output the profile cannot honor). Content-policy refusals stay completed responses (§5).
Avoid: try / except around PAI UserError as the way to learn that a model cannot do JSON schema or parallel tool calls. Read the profile, then do not send the unsupported option.

10. Input adapter (Responses JSON → agent)

Typical mapping (names illustrative):

Request field Agent / run
model (provider/model id) registry.get_model
input (string or item list) user prompt + optional extra messages
instructions / resolved stored prompt runtime instructions
tools / MCP / file_search assembled toolsets (§7)
sampling, max_tokens, thinking, etc. resolved ModelSettings
previous_response_id tip: continue_run + same conv; fork: fork_run + minted ids (§8)
conversation / LCORE conversation id load turns → PAI messages (persist mapper, inverse)
stream run_stream_events vs run

Keep today’s request sanitization (strip secrets from echoes, bound sizes) on the way in and on the way out.

11. Output adapter (agent → Responses)

Non-stream: build one OpenAI-compatible Responses object: id = PAI run_id, status, output items (messages, MCP/file_search tool items), usage, echoed model / instructions / applied settings, warnings from the resolver.

Stream: project PAI stream events into OpenAI Responses SSE (response.created, output-item deltas, completed / failed). Do not reuse query’s LCORE SSE event names on this route.

Failures:

  • Validation / cannot-start / output-contract → HTTP 400 (structured error models already in tree).
  • Auth / quota → existing 401 / 403 / 429.
  • Provider outage → 502/503 as today.
  • Shield refusal → 200 completed (or stream completed) with refusal content.
  • Mid-run tool or model error → failed Responses object / stream failed event; persist ErrorItem.
