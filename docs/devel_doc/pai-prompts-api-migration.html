PAI migration — prompts API (local store)

Lightspeed Core Stack (LCORE) · OGX removal notes · Sep 2026

This document covers moving the OpenAI-compatible Prompts API (/v1/prompts + responses.prompt) off OGX into LCORE: resource shape, template syntax, validation, local DB schema, and injection into pydantic-ai agents.

1. Decision in one sentence

After OGX removal, LCORE owns a local versioned prompt store behind /v1/prompts; when /v1/responses references prompt: { id, version?, variables? }, LCORE renders the template and passes it to the agent as runtime instructions — never as output_type, and never forwarded to a backend prompt store.

Preferred baseline: local DB (prompt + prompt_version + prompt_version_variable) · Mustache-style {{var}} substitution with create-time validation · inject via agent.run(..., instructions=rendered) while keeping LCORE defaults as static Agent(instructions=...).

2. Prompt resource

A prompt is a stored, versioned system-instruction template managed by /v1/prompts and referenced on /v1/responses as prompt: { id, version?, variables? }. Versus instructions: same system channel after render, but instructions is inline for one request; prompt is a reusable id + optional {{placeholders}}. (Not output_type / PromptedOutput — those shape the return value.)

Attribute Type Notes
prompt_id string pmpt_ + 48 lowercase hex
version int (≥ 1) Immutable history; bumps on update
is_default bool Whether this version is the current default
prompt string Template text with {{placeholders}}
variables list[string] Declared placeholder names 
{
  "prompt": {
    "id": "pmpt_…",
    "version": "1",
    "variables": {
      "role": { "type": "input_text", "text": "Kubernetes expert" },
      "topic": { "type": "input_text", "text": "OpenShift" }
    }
  }
}

Substitution values may be strings or Responses content objects (input_text / input_image / input_file). Initial LCORE render can require text-only.

3. What changes when removing OGX

Today (with OGX) After (LCORE-owned)
prompts.py → client.prompts.* prompts.py → local PromptStore (SQLAlchemy)
Create/update validation inside OGX Same rules reimplemented in LCORE (see §5)
responses.prompt may be forwarded for server-side expansion LCORE resolves + renders; strip prompt from outbound model params
HTTP response can still echo prompt Keep echoing the client’s prompt object for API compatibility
Agent gets instructions somehow via OGX path Rendered string → pydantic-ai runtime instructions (see §7)
Keep the public API shape (/v1/prompts CRUD + responses.prompt) so existing clients stay compatible; only the storage and resolution owner changes.

4. Database schema

Reasonable normal form: identity, immutable versions, declared variables as child rows. Default version is a column on prompt, not a denormalized is_default flag on every version row.

prompt ├── id (PK) pmpt_ + 48 hex ├── default_version (NOT NULL) ├── created_by, created_at, updated_at │ └──<1:N>── prompt_version ├── (prompt_id, version) (PK) ├── prompt_id (FK → prompt.id) ON DELETE CASCADE ├── prompt_text ├── created_by, created_at │ └──<1:N>── prompt_version_variable ├── (prompt_id, version, name) (PK) └── (prompt_id, version) (FK → prompt_version) ON DELETE CASCADE Optional deferred FK: prompt (id, default_version) → prompt_version (prompt_id, version)

4.1 Keys

Key Type Meaning
prompt.id PK Template id
prompt_version.(prompt_id, version) PK One immutable revision
prompt_version.prompt_id FK → prompt.id Version belongs to template
prompt_version_variable.(prompt_id, version, name) PK Declared variable for that revision
prompt_version_variable.(prompt_id, version) FK → prompt_version Variables belong to a revision
prompt.(id, default_version) FK (deferred) → prompt_version Which revision is default

4.2 API ↔ storage map

API field Storage
prompt_id prompt.id
version prompt_version.version
prompt prompt_version.prompt_text
variables rows in prompt_version_variable
is_default computed: prompt.default_version = version
Optional simplification: store variables as JSON on prompt_version and drop the child table. Fewer joins, weaker uniqueness / query constraints. Prefer the child table for parity with create-time validation.

5. Template format and validation

OpenAI-compatible / current OGX rule: Mustache-style placeholders only. OGX validates with: 

re.findall(r"{{\s*(\w+)\s*}}", prompt_text)
  • Placeholder form: {{name}} (optional spaces: {{ name }})
  • Name must match \w+ (letters, digits, underscore)
  • Every placeholder in the text must be listed in variables
  • Declared-but-unused names are allowed
  • Not Jinja: no {% if %}, filters, loops, dotted paths
LCORE must reimplement this validation on create and update once OGX is removed. Render-time validation (missing / extra substitution values on /v1/responses) is a second check.

5.1 Valid examples

{
  "prompt": "You are a {{role}}. Focus on {{topic}}.",
  "variables": ["role", "topic"]
}
{
  "prompt": "Summarize: {{ text }}",
  "variables": ["text"]
}
{
  "prompt": "You are a helpful assistant. Be concise.",
  "variables": []
}
{
  "prompt": "Hello {{name}}",
  "variables": ["name", "unused_extra"]
}

Declared-but-unused unused_extra is OK.

5.2 Invalid / edge cases

Case Example Why
Undeclared var "prompt": "Hi {{role}}", "variables": [] role not in variables
Hyphen in name {{user-name}} - not in \w
Dotted path {{user.name}} Not a single \w+ token
Single braces {name} Not a placeholder (literal text)
Jinja control {% if x %}...{% endif %} Unsupported in this format
Empty prompt "" Rejected by request model (min_length=1)
Literal braces Use {JSON} objects carefully OK if not {{…}}

Note: rlsapi’s system prompt path uses Jinja2 separately. That is not the Prompts API format. Keep Prompts API Mustache-only for OpenAI compatibility.

6. End-to-end flows

6.1 CRUD

Client → POST/GET/PUT/DELETE /v1/prompts → PromptStore (validate + persist) → local DB

6.2 Use on responses

POST /v1/responses { prompt: {id, version?, variables?}, input, … } → get_system_prompt(instructions) # LCORE / profile defaults → if prompt set: PromptStore.render(...) # load version, substitute → build_agent(instructions=defaults) # static layer → agent.run(..., instructions=rendered) # runtime layer → echo original prompt on HTTP response; do not send prompt.id to model wire

7. Injecting into pydantic-ai agents

pydantic-ai prefers instructions over system_prompt, and supports three layers:

Layer API Use in LCORE
Static Agent(instructions=...) Profile / deployment defaults (stable cache prefix)
Dynamic @agent.instructions + deps Optional; long-lived agents that resolve from store via deps
Runtime agent.run(..., instructions=...) Preferred for per-request stored prompt templates
Recommended injection: keep LCORE defaults on the Agent as static instructions; pass the rendered stored prompt as runtime instructions on run / run_stream_events. Same helper for responses, query, streaming, A2A. 
# defaults only (profile / get_system_prompt)
agent = build_agent(client, responses_params_with_defaults, config)

rendered = await prompt_store.render(
    prompt_id=request.prompt.id,
    version=request.prompt.version,
    variables=request.prompt.variables,
)

# do not overwrite Agent(...) with the template alone —
# pass it as runtime instructions for this run
await agent.run(user_prompt, instructions=rendered)
# or: async with agent.run_stream_events(user_prompt, instructions=rendered)

Today build_agent already does Agent(..., instructions=responses_params.instructions). Migration splits “defaults” vs “referenced template” across static vs runtime layers instead of flattening everything into the constructor.

Avoid: mapping stored prompts to output_type / PromptedOutput · using system_prompt (history / reinjection pitfalls) · forwarding prompt.id to OGX/the model transport after cutover · stuffing the template only into constructor instructions and losing the static/runtime split.
